# Consistent Hashing（一致性哈希）算法详解

> 本文档是 [ROUTING_POLICIES_ZH.md](./ROUTING_POLICIES_ZH.md) 中「Consistent Hashing」策略的深入拆解，
> 包含环形拓扑原理、Chord/Dynamo 溯源与迁移量分析等细节。主文档仅保留概览。

**实现**：`src/policies/consistent_hashing.rs` — 预计算哈希环，支持 header 直连与 routing key 亲和。

## 第一性原理降维

一致性哈希优化的**不是实时负载**，而是**拓扑变化下的映射稳定性**。普通取模 $\text{hash}(k) \bmod n$ 在 $n$ 变化时几乎全部重映射；一致性哈希把 Worker 和 key 都映射到同一个环上，key 顺时针找第一个健康 Worker：

$$
\text{扩缩容时迁移的 key 比例} \approx \frac{1}{N} \quad (\text{而非取模的近 } 100\%)
$$

代码中环由 `WorkerRegistry` 预构建缓存（非每请求重建），保证 $O(\log n)$ 二分查找 + $O(k)$ 跳过连续不健康节点。其决策优先级为：

1. `X-SMG-Target-Worker`：按下标直连（$O(1)$）
2. `X-SMG-Routing-Key`：显式 key 一致性哈希
3. 隐式 key（authorization/x-forwarded-for/cookie 等稳定头）做会话亲和
4. 随机兜底

## 高阶结构化类比

经典的 **Chord DHT / Amazon Dynamo** 环形拓扑——用「环 + 顺时针查找」把「成员变更的爆炸半径」限制在 $1/N$。

### 什么是「环形拓扑」

把哈希值空间（如 $[0, 2^{32})$ 或 $[0, 2^{160})$）想象成一个**首尾相接的圆环**：最大值的下一个位置又回到 $0$。然后：

1. **节点上环**：对每个 Worker（节点）用哈希函数 $\text{hash}(\text{节点标识})$ 算出一个位置，把它「钉」在环上。
2. **数据/请求上环**：对每个 key（这里是前缀哈希或 routing key）同样算 $\text{hash}(k)$，落到环上某点。
3. **归属规则**：从 key 的位置**顺时针**走，遇到的**第一个节点**就是它的归属 Worker（若不健康则继续顺时针跳到下一个）。

这样「查找」退化为「在有序的节点位置数组里做二分查找」——即代码中的 $O(\log n)$。

```text
        0 / 2^32
          ┌───●B───┐
       ●A │        │ key k  → 顺时针遇到的第一个节点是 C，归属 C
          │        ●C
          └───●D───┘
   环上顺序: A → B → C → D → （回到 A）
```

### Chord DHT（2001，MIT）

- **背景**：P2P 分布式哈希表，目标是在没有中心目录的情况下，让任意节点都能高效定位「某个 key 存在哪个节点」。
- **核心贡献**：
  - 将节点与 key 映射到同一个 $2^{m}$ 的环（**identifier ring**）；key 归属其顺时针后继节点（successor）。
  - 用 **finger table（指针表）** 让每个节点缓存若干「间隔指数级增大」的后继，从而把查找从 $O(N)$ 降到 $O(\log N)$ 跳。
  - 节点加入/离开时，只影响其**相邻区间**的 key，迁移量约 $1/N$。
- **对本项目的映射**：我们不需要 finger table（Worker 数量少、环在网关本地预构建），但「节点与 key 同环、顺时针找后继」的**归属规则完全一致**。

### Amazon Dynamo（2007）

- **背景**：亚马逊购物车等高可用存储，追求「永远可写」与弹性伸缩。
- **在一致性哈希上的关键改进**：
  - **虚拟节点（virtual nodes / vnodes）**：每个物理节点在环上放置**多个**虚拟位置，解决「节点少时环分布不均、扩容负载迁移不均」的问题。这正是本文档下方“极限”里提到的**虚拟节点缓解均匀性**的来源。
  - **副本与 N/R/W**：key 顺时针的前 $N$ 个节点各存一份副本（本项目不涉及存储副本，仅借用环定位思想）。
- **对本项目的映射**：`HashRing` 为每个 Worker 生成多个虚拟节点以改善均匀性，思路直接来自 Dynamo 的 vnodes。

### 为什么迁移量是 $1/N$

普通取模 $\text{hash}(k) \bmod n$：当 $n$ 从 $N$ 变为 $N+1$ 时，**绝大多数 key 的取模结果都会变**，接近 100% 重映射。
环形拓扑下增删一个节点，只有**落在该节点所负责的那段环弧**上的 key 需要改归属，其余 key 的「顺时针后继」不变——受影响比例约为该弧长占整个环的比例，即约 $1/N$。这就是「成员变更的爆炸半径被限制在 $1/N$」的直观来源。

## 边界与反模式

- **边界**：与 Manual 的分界线是**扩容行为**。一致性哈希在加节点时**会**重分布约 $1/N$ 的 key；Manual 加节点时**完全不**重分布已有会话。
- **极限**：Worker 数很少（如 2~3 个）时环的均匀性差，需虚拟节点缓解。
- **反模式**：把一致性哈希当负载均衡器用——它天然不感知实时负载，热 key 会持续压在同一节点。

## 演进动机

推翻了「取模映射」在动态拓扑下的可用性假设，是所有需要「稳定亲和 + 弹性伸缩」场景的基石。

## 参数配置

一致性哈希在 `PolicyConfig` 中是**无字段变体**（`PolicyConfig::ConsistentHashing`，见 `src/config/types.rs`），即**没有需要设置的策略级参数**——环由 `WorkerRegistry` 用固定哈希函数构建，虚拟节点密度等在 `HashRing` 内部固定。

因此它的「配置」体现在**请求头**（决定路由 key 来源）而非策略参数上，决策优先级如下：

| 请求头 / 来源 | 作用 | 优先级 |
|---|---|---|
| `X-SMG-Target-Worker` | 按下标直连指定 Worker（$O(1)$，绕过哈希环） | 最高 |
| `X-SMG-Routing-Key` | 显式路由 key，做一致性哈希亲和 | 次高 |
| 隐式 key（`authorization` / `x-forwarded-for` / `cookie` 等稳定头） | 无显式 key 时用于会话亲和 | 中 |
| 随机兜底 | 上述均无时随机选健康 Worker | 最低 |

> 若需调节环的均匀性（虚拟节点数）等，属于 `HashRing` 的内部实现，当前不作为对外可配置参数暴露。

## 下游 Worker 节点增删对本策略的影响

一致性哈希对拓扑变更的处理正是其**设计初衷**——把成员变更的爆炸半径限制在 $1/N$。环由 `WorkerRegistry` 在 worker 变更时重建并缓存，再传入策略：

- **新增 Worker**：新节点上环后，仅**其所负责的那段环弧**上的 key 改归属到它，约 $1/N$ 的会话被重分布；这部分会话丢失原节点的缓存/上下文，需在新节点重建，其余会话亲和完全不变。
- **移除 Worker**：被移除节点所负责的 key 顺时针改由**后继节点**承接，同样约 $1/N$ 规模迁移；未落在该弧上的 key 归属不变。
- **不健康跳过**：节点临时不健康时并不重建环，而是在查找时 $O(k)$ **顺时针跳过**连续的不健康节点，恢复健康后归属自动回到原节点（区别于永久移除）。
- **少 Worker 场景**：Worker 数少时单个节点占据的环弧大，增删引起的迁移比例波动更明显，需靠虚拟节点均匀化。

**一句话**：增删仅重分布**约 $1/N$ 的会话**（远优于取模的近 100%），是本策略的核心优势；临时不健康只做顺时针跳过、不触发重分布，恢复后亲和自动复原。

## 优缺点、使用场景、局限性与优化迭代方向

### 优点

- **弹性伸缩迁移小**：扩缩容仅重分布约 $1/N$ 的 key，远优于取模的近 100% 重映射。
- **稳定会话亲和**：相同 routing key 恒定映射到同一 Worker，天然支持会话粘性。
- **查找高效**：环预构建缓存，$O(\log n)$ 二分 + $O(k)$ 跳过不健康节点。
- **分布式无状态复现**：各节点从一致 worker 列表本地重建环，多节点亲和天然一致，无需同步。
- **多级路由优先级**：支持 `X-SMG-Target-Worker` 直连、显式/隐式 key 亲和、随机兜底的清晰决策链。

### 缺点

- **不感知实时负载**：纯拓扑映射，热 key 会持续压在同一节点，无法自动均衡。
- **少 Worker 时分布不均**：2~3 个 Worker 时环均匀性差，需虚拟节点缓解。
- **扩容会破坏部分亲和**：与 Manual 相比，加节点时约 $1/N$ 的会话会被重分布。

### 使用场景

- **多租户会话**、需要会话粘性且**频繁弹性扩缩容**的服务。
- 希望亲和能在多 router 节点间无状态复现（不依赖策略状态同步）的分布式部署。
- 可接受「扩容时少量会话迁移」以换取弹性的场景。

### 局限性

- 无负载感知，倾斜的 key 分布（热 key）会导致节点间负载不均。
- 亲和依赖 key 的稳定性；若隐式 key（cookie/IP 等）不稳定，亲和会失效。
- 扩缩容瞬间被重分布的 $1/N$ 会话会丢失原节点的缓存/上下文。

### 优化迭代方向

- **负载感知加权环**：综合静态容量与实时负载调整映射或候选选择，缓解热 key 倾斜（详见下节）。
- **有界一致性哈希**：引入负载上限（bounded-load consistent hashing），超载时溢出到后继节点。
- **虚拟节点自适应**：按 Worker 数量与容量差异动态调整 vnode 密度，改善少节点均匀性（详见下节）。
- **迁移平滑**：扩容时对被重分布的会话做缓存预热或渐进迁移，降低亲和中断代价。

#### 深入：负载感知加权环的实现方案

负载感知加权环需要在三个目标间权衡：**映射稳定性、缓存亲和性、实时负载均衡**。常见方案如下：

| 方案 | 核心机制 | 优点 | 局限与适用场景 |
|---|---|---|---|
| **按权重分配虚拟节点** | Worker 的 vnode 数量与权重成比例：$V_i = V_{base} \times W_i$；权重可取 $W_i = C_i \times (1-U_i)$ | 实现简单，可直接复用现有哈希环 | 权重变化会重建部分环；vnode 数量离散。适合容量异构、负载变化较慢的场景 |
| **加权区间环** | 不增加 vnode，直接让 Worker 占据与权重成比例的哈希区间 | 内存占用小，权重表达精确 | 调整区间边界较复杂，可能引发较多 key 迁移。适合节点少、权重稳定的场景 |
| **有界负载一致性哈希** | 首选节点超过上限 $L_i > \alpha \times L_{avg}$ 时，沿环寻找下一个未超载节点 | 保留大部分亲和性，并提供明确负载上界 | 需要准确负载计数，最坏情况需扫描多个节点。适合缓存与推理路由 |
| **环上多候选选择** | 从首选位置取连续 2～3 个候选，选择归一化负载 $L_i/C_i$ 最低者 | 环无需频繁重建，对瞬时负载响应快 | 不保证严格亲和；需要实时负载视图。适合长短请求混合、负载波动明显的场景 |
| **动态权重环** | 周期性根据队列、延迟 EWMA、GPU/KV Cache 利用率等指标重新计算权重 | 能适应持续变化的容量与负载 | 更新过快会导致路由抖动和缓存失效，需配合 EWMA、滞回阈值、最小更新周期和单次变化上限 |
| **固定环 + 负载溢出** | 哈希环只确定首选 Worker；达到软上限后溢出到后继或低负载备用 Worker | 正常情况下亲和性最强，环结构稳定 | 热 key 仍可能集中，溢出节点缓存命中率较低。适合 Prefix/KV Cache 复用场景 |

负载权重可以综合静态容量与动态指标，例如：

$$
W_i = \frac{C_i}{aQ_i + bT_i + cU_i + \epsilon}
$$

其中 $C_i$ 是 Worker 容量，$Q_i$ 是排队长度，$T_i$ 是延迟 EWMA 或预计 token 计算量，$U_i$ 是 GPU/KV Cache 利用率。生产实现应对指标做平滑，并避免因短时抖动频繁重建哈希环。

**对 LLM Router 的推荐组合**：采用“**静态容量决定 vnode 数量 + 环上多候选 + 有界负载溢出**”。请求先通过稳定哈希得到首选 Worker，再取少量后继候选；首选未超过软上限时维持缓存亲和，超限后选择归一化负载最低的候选。相比直接按实时指标重建环，该组合能更好地兼顾 Prefix/KV Cache 命中率、异构 Worker 容量和实时负载均衡。

#### 深入：有界一致性哈希（bounded-load）的常见方案

当前 `consistent_hashing.rs` 是**纯**一致性哈希，不感知负载，热 key 会持续压在同一节点（见上文「局限性」）。有界一致性哈希在环查找时给每个节点加一个**负载上限**，超限则顺延到后继，从而在保持亲和/低迁移的同时避免热点过载。常见方案如下：

| 方案 | 核心机制 | 负载/迁移保证 | 工程实现 |
|---|---|---|---|
| **CHBL**（Google 2016，*Consistent Hashing with Bounded Loads*） | 容量上限 $c = \lceil (1+\varepsilon)\cdot \tfrac{\text{总负载}}{N} \rceil$，key 顺时针找第一个**未满**节点 | 任意节点 ≤ $(1+\varepsilon)$ 倍均值；期望迁移 $O(1/\varepsilon^2)$ | HAProxy `hash-balance-factor`、Envoy `ring_hash`(bounded)、Vimeo `consistent`(Go) |
| **Rendezvous/HRW + 封顶** | 对所有节点算权重排序，跳过已达上限者选次高 | 无需 vnode 即较均匀，少节点友好 | mailgun/groupcache 等 |
| **Maglev**（Google 2016） | 查找表 + 近均匀填充，追求均匀性 + 最小中断 | 表级近均匀、重建中断小 | Envoy `maglev` 内置 |
| **Jump Hash + 容量约束** | Jump Consistent Hash（$O(\ln N)$、内存 $O(1)$）叠加节点容量/权重 | 无需存环，扩展成本低 | Lamping & Veach 算法 |

**对本项目最贴合的落地路径**：**CHBL**。只需在现有 `HashRing` 顺时针查找时加一个判据——「节点负载 $\le (1+\varepsilon)\times$ 平均」，超限则跳到后继节点——即可复用已有的全局负载视图（Worker 状态同步），改动最小，且天然与 `X-SMG-Routing-Key` 亲和链路兼容。

#### 深入：虚拟节点自适应的实现方案

当前 `HashRing` 的 vnode 密度是内部固定的。虚拟节点自适应旨在让每个物理 Worker 的 vnode 数量/权重随**节点数、容量差异、实时负载**动态调整，以改善均匀性、支持异构 Worker 与弹性伸缩。常见方案如下：

| 方案 | 核心机制 | 优点 | 局限与适用场景 |
|---|---|---|---|
| **按节点数自适应密度** | vnode 数 = $f(N)$，节点少时每节点放更多 vnode、节点多时降密度 | 改善「少节点分布不均」，同时抑制多节点时的环内存/查找膨胀 | 仅解决均匀性，不感知容量/负载。适合同构 Worker |
| **按容量加权 vnode** | vnode 数 $\propto$ 节点容量/权重，强机放更多 vnode | 表达异构容量，实现简单可复用现有环 | 权重变化引发局部重建；vnode 数离散。适合**异构 GPU Worker**、权重变化慢 |
| **负载感知动态重加权** | 周期性按实时负载调整各节点 vnode 权重（过载减、空闲加） | 适应持续变化的负载，可复用全局负载视图 / `LoadMonitor` | vnode 增删引起局部重映射，需迟滞/最小更新周期防抖动 |
| **Cassandra 分配算法** | 新节点 token 位置**主动填补当前最不均匀的环弧**（基于 RF 优化），而非随机 | 自适应放置、均匀性优于随机 vnode | 需全局环视图与分配计算。适合节点频繁增删 |
| **Dynamo 等大小分区** | 环切成固定数量**等大分区**，节点按容量认领分区数，扩缩容按分区迁移 | 均匀性与迁移量可控、可预测 | 分区粒度固定，需预设分区数。适合弹性伸缩 |
| **Maglev / 查找表法** | 查找表近均匀填充替代显式 vnode | 天然规避少节点不均，重建中断最小 | 表重建有成本；亲和粒度受表大小限制 |

**对本项目最贴合的落地路径（由简到难）**：① **按 $N$ 调密度**——最简单，只改构建环时的 vnode 数计算；② **按容量加权**——支持异构 GPU Worker；③ **负载感知重加权**——效果最好但需处理重映射抖动，可复用已有负载视图。与「有界一致性哈希」组合时，建议 vnode 只承担**静态容量/均匀性**表达，实时负载均衡交给 CHBL 的溢出判据，避免两者都频繁改动环而放大抖动。
