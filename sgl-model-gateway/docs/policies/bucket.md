# Bucket（分桶）算法详解

> 本文档是 [ROUTING_POLICIES_ZH.md](./ROUTING_POLICIES_ZH.md) 中「Bucket」策略的深入拆解，
> 包含双层机制、边界重划算法与关键数据结构等细节。主文档仅保留概览。

**实现**：`src/policies/bucket.rs` — 按 **请求长度（字符数）** 把 Prefill Worker 划分为若干「桶」，每个 Worker 负责一段长度区间；后台线程按滑动窗口内的真实负载**动态重划边界**，主要服务 PD（Prefill/Decode 分离）场景的 **prefill_policy**。

## 第一性原理降维

Bucket 的核心洞察是：**Prefill 阶段的计算成本近似正比于输入长度**。因此，与其在请求到达时估计每个 Worker 的排队/缓存状态，不如**按输入长度做静态分片**——让"长请求"和"短请求"分别落到固定的 Worker，从而把「重活」隔离开，避免长短请求混在同一实例上互相拖尾。

它把连续的长度轴 $[0, \infty)$ 切成 $N$ 段（$N$ = prefill worker 数），每个 Worker 认领一段区间 `[min, max]`：

$$
\text{route}(x) = \text{Worker}_k \quad\text{s.t.}\quad x \in [\text{min}_k,\ \text{max}_k]
$$

其中 $x$ 是本次请求的**字符数**（`request_text.chars().count()`，故 `needs_request_text() = true`）。选桶用**二分查找** `find_boundary`（边界有序），复杂度 $O(\log N)$。

**初始边界**是等分的：`gap = l_max / worker_cnt`（`l_max` 初值 4096），最后一个桶的上界扩到 `usize::MAX` 兜底任意超长请求。

## 双层机制：静态分桶 + 动态再平衡

**① 请求期（select_worker）——分桶为主、失衡时降级为最小负载**

每次选 Worker 时，先读取滑动窗口内各 Worker 的累计字符负载 `chars_per_url`，用**双阈值**判断是否失衡（与 Cache Aware 同构）：

$$
\text{imbalanced} \iff (\text{max} - \text{min}) > \tau_\text{abs} \;\wedge\; \text{max} > \tau_\text{rel} \cdot \text{min}
$$

- **未失衡** → 走 **Bucket 分桶**：按请求长度二分命中所属区间的 Worker（长度决定归属，可预测、稳定）。
- **已失衡** → 临时降级为**最小负载优先**：直接选当前累计字符最少的 Worker，牺牲长度亲和换取快速再平衡。

选定后 `post_process_request` 会：把本次 `char_cnt` 累加到该 URL 的负载、生成一条带时间戳的 `SequencerRequest` 入队，并**淘汰超出滑动窗口**（`period = bucket_adjust_interval_secs × 1000` ms）的历史请求、回滚其负载。即负载统计是一个**时间滑动窗口**，只反映最近一段时间的流量。

**② 后台期（adjust_boundary）——按负载分位重划边界**

后台线程每隔 `bucket_adjust_interval_secs`（默认 5s）对每个模型的桶做一次边界重算，目标是让**每个桶承担的总负载尽量均等**：

1. 计算目标单桶负载 `new_single_bucket_load = 总负载 / worker_cnt`；
2. **迟滞（hysteresis）保护**：若新旧单桶负载相差不到 2 倍（且旧值非 0），认为无需调整，直接跳过——避免边界频繁抖动；
3. 否则把窗口内所有请求长度**排序**，按"累积负载达到单桶目标"为切点，依次给每个 Worker 划定新的 `[min, max]` 区间（本质是**按负载做等分位切分**，而非按长度等分）。

这样，如果短请求特别多，短请求区间会被切得更细（多个 Worker 分摊）；长请求稀疏，则由少数 Worker 覆盖大长度区间——**边界随真实长度分布自适应**。

## 关键数据结构

| 字段 | 作用 |
|---|---|
| `boundary: Vec<Boundary>` | 有序的 `{url, [min,max]}` 列表，二分选桶的依据 |
| `chars_per_url` | 各 Worker 在滑动窗口内的累计字符负载（失衡判断 + 重划分位） |
| `request_list: VecDeque<SequencerRequest>` | 按时间排序的请求队列，用于滑动窗口过期淘汰 |
| `period` | 滑动窗口长度（ms），等于调整间隔 |

桶以 `normalize_model_key(model_id)` 为 key 隔离，不同模型各自维护独立分桶与负载窗口。Worker 增删（`add_prefill_url` / `remove_prefill_url`）会重置边界并同步 `chars_per_url`。

## 高阶结构化类比

类似磁盘的**分区/分级存储**或数据库的**范围分片（range sharding）**——按 key（这里是"请求长度"）的区间把负载路由到固定分片，再用后台任务按实际数据分布**动态调整分片边界**（类比 HBase Region Split / 自动 rebalance）。也可类比 CPU 调度里把长短任务分到不同队列的**多级队列**思想。

## 边界与反模式

- **边界**：适用范围窄，主要作为 PD 分离的 **prefill_policy**（长度 ≈ prefill 计算量时最有效），不建议作为通用 Regular 流量默认策略。
- **与 Cache Aware 的区别**：两者都用"双阈值失衡检测 + 降级"，但 Bucket 的一等公民是**请求长度分片**（无状态、可预测），Cache Aware 的一等公民是**前缀缓存亲和**（有状态）。Bucket 不感知 KV 缓存。
- **反模式**：
  - 当请求长度与真实计算成本**弱相关**时（如长度相近但难度差异大），长度分桶失去意义。
  - 迟滞阈值（2×）设置过松会导致边界长期不更新、分桶僵化；过紧则边界抖动、路由不稳定。
  - 长度分布极度长尾时，个别覆盖超长区间的 Worker 可能持续偏载，依赖失衡降级兜底。

## 演进动机

在 PD 分离下，prefill 是"算力密集、成本随长度线性增长"的阶段。把"按长度分片 + 按负载自适应重划边界"结合，既保留了**同长度请求路由稳定**的可预测性，又通过后台再平衡与请求期失衡降级，避免了静态分片在流量倾斜时的僵化——这是为"长度即成本"这一 prefill 特性量身定制的均衡器。

## 参数配置

策略参数定义见 `PolicyConfig::Bucket`（`src/config/types.rs`），失衡判据与 Cache Aware 同构（双阈值「与」逻辑）。

| 参数 | 类型 | 含义 | 调参影响 |
|---|---|---|---|
| `balance_abs_threshold` | `usize` | 失衡判定的**绝对**差阈值：窗口内各 Worker 累计字符负载 `max - min` 超过它才可能触发失衡 | 调小 → 更早降级为最小负载（偏均衡）；调大 → 更容忍偏差（偏长度亲和） |
| `balance_rel_threshold` | `f32` | 失衡判定的**相对**比阈值：`max > rel × min` 才触发失衡 | 与 abs 为「与」关系，二者同时满足才判失衡 |
| `bucket_adjust_interval_secs` | `usize` | 桶边界调整周期（秒），同时等于负载滑动窗口长度（`period = 此值 × 1000` ms） | 调小 → 边界更快跟随流量但样本少、易抖动；调大 → 边界稳但对流量变化反应慢 |

> 失衡判据：$(\text{max}-\text{min}) > \texttt{balance\_abs\_threshold} \wedge \text{max} > \texttt{balance\_rel\_threshold} \times \text{min}$（`src/policies/bucket.rs`）。
>
> 另有两个**内部常量**（非对外参数）：初始长度上界 `l_max = 4096`（用于首次等分边界），以及边界重划的**迟滞阈值 2×**（新旧单桶负载相差不足 2 倍则跳过调整，防抖动）。

## 下游 Worker 节点增删对本策略的影响

Bucket 的私有状态是**长度区间边界 `boundary`** 与**滑动窗口负载 `chars_per_url`**，两者都与 Worker 集合强绑定。增删由 `add_prefill_url` / `remove_prefill_url` 处理（见 `src/policies/bucket.rs`）：

- **新增 Worker**：`add_prefill_url` 会**重置桶边界**并同步 `chars_per_url`，把长度轴重新按新的 Worker 数（$N \to N+1$）等分/重划。这意味着**几乎所有长度区间的归属都会变化**——原本落在某桶的请求可能改由不同 Worker 承接，长度亲和被短暂打破，直到后台 `adjust_boundary` 按新分布收敛。
- **移除 Worker**：`remove_prefill_url` 同样重置边界并清理该 Worker 的负载条目，其负责的长度区间被合并到相邻 Worker。
- **与哈希类的关键区别**：Bucket 的边界是**按 Worker 数等分/按负载分位**切分的，增删不是「$1/N$ 局部迁移」而是**边界整体重划**，扰动范围远大于一致性哈希/前缀哈希。
- **收敛依赖窗口**：重划后需要若干个 `bucket_adjust_interval_secs`（默认 5s）窗口积累新样本，边界才随真实长度分布重新稳定；迟滞保护（2×）会进一步延缓收敛。

**一句话**：增删会触发**桶边界整体重置与重划**，短期内长度亲和被打破、路由归属大范围变化，需靠后台再平衡在若干窗口后重新收敛——是对拓扑变更较敏感的策略之一。

## 优缺点、使用场景、局限性与优化迭代方向

### 优点

- **长短请求隔离**：把「重活」按长度隔离到固定 Worker，避免长短请求混跑互相拖尾，降低尾延迟。
- **路由可预测**：同长度请求稳定落到同一桶，选桶 $O(\log N)$，行为易理解、易观测。
- **自适应边界**：后台按负载分位重划边界，短请求多则细分、长请求稀疏则合并，随分布自适应。
- **失衡兜底**：请求期双阈值失衡检测 + 降级最小负载，防止静态分片在倾斜时僵化。
- **模型隔离**：按 `model_id` 隔离分桶与负载窗口，多模型互不干扰。

### 缺点

- **适用面窄**：主要服务 PD 分离的 prefill_policy，不适合作通用 Regular 流量默认策略。
- **依赖「长度≈成本」假设**：长度与真实计算成本弱相关时（如长度相近但难度差异大）分桶失去意义。
- **不感知缓存**：纯长度分片，不考虑 KV Cache 亲和，与 cache_aware 正交。
- **参数敏感**：迟滞阈值（2×）过松则边界僵化、过紧则抖动。

### 使用场景

- **PD 分离部署**中作为 prefill_policy，输入长度近似等于 prefill 计算量的场景。
- 请求长度分布跨度大、需要把长短请求分流以稳定尾延迟的服务。
- 长度分布随时间变化、需要边界自适应重划的流量。

### 局限性

- 长度分布极度长尾时，覆盖超长区间的 Worker 可能持续偏载，仅靠失衡降级兜底。
- 冷启动/流量突变时滑动窗口样本不足，边界需若干周期才收敛。

以下四点是 Bucket 因其「无状态字符数分片」本质而带来的**系统性局限**，也是其适用边界（单轮、无前缀复用、prefill 成本≈长度）的直接体现：

1. **字符数 ≠ token 数（分桶度量偏差）**：分桶依据是 `request_text.chars().count()`，而 prefill 计算量真正正比于 **token 数**。二者关系随语言/内容非线性（中文 1 字符≈ 1~2 token、英文若干字符才 1 token、代码/公式差异更大），故字符数只是 token 的**粗代理**。同一字符桶内不同请求的真实 prefill 成本可能相差很大，使「长度即成本」假设与边界划分失真。
2. **不感知 Worker 的 cache 命中**：Bucket 只按长度分片 + 滑窗负载降级，**完全不感知 KV Cache**。同一前缀的两个请求可能因长度落入不同桶而被拆到不同 Worker，无法复用 KV——与 Cache Aware 的前缀亲和目标正相反。
3. **滑窗淘汰的请求未必已完成 prefill（负载度量与真实占用错位）**：滑动窗口按时间淘汰旧样本来估算累计字符负载，但被淘汰的请求**不保证 prefill 已结束**。于是窗口内统计的「累计字符」既非当前真实在算的负载、也非已完成吞吐量，只是「最近一段时间进入的请求量」。长请求 prefill 慢、可能在其样本已被淘汰后仍占用 GPU，导致边界重划依据的负载视图**系统性低估长请求 Worker 的真实占用**。
4. **多轮 session 在多 Worker 间漂移 → 大规模 KV miss（最本质）**：同一 session 多轮对话中上下文**逐轮变长**，字符数会跨越桶边界被路由到**不同 prefill Worker**；而多轮的最大价值恰恰是复用前几轮的 KV Cache。Bucket 无 session 亲和概念，长度一变就换 Worker，等于每轮都在新 Worker 上重新 prefill 整个历史上下文，形成**随轮数放大的 KV cache miss**——轮数越多、上下文越长，浪费越严重。

### 优化迭代方向

- **成本模型升级（对应局限 1、3）**：用 **token 数**替代字符数提升「长度→成本」映射精度（代价是选路前需分词，失去 bucket 「无需分词」的轻量优势，或对字符数按语言/模型乘经验系数校正）；进一步可以「请求进入/完成」配对的**在途成本**（active prefill cost）替代纯时间滑窗，或在请求真正完成 prefill 时才从负载中扣减，避免长请求 Worker 负载被低估。
- **多维分桶**：在长度之外引入难度/优先级等维度，缓解「长度相近成本不同」的失效。
- **自适应迟滞**：按边界抖动频率动态调整迟滞阈值，在稳定与灵敏间自平衡。
- **与缓存/会话亲和融合（对应局限 2、4）**：在长度分桶基础上叠加轻量前缀亲和以兼顾 KV 复用；对**多轮会话**尤其应叠加 **session 粘性**（用 routing key 固定 session→worker，覆盖长度分桶），避免上下文变长导致的跨 Worker 漂移与重复 prefill；若前缀复用价值高，应直接改用 Cache Aware / Consistent Hashing / Manual。
- **长尾专桶**：为超长请求设置弹性专桶或独立小池，避免单 Worker 长尾偏载。
