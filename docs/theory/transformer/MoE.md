# MoE：从稠密计算到条件计算的第一性原理

> Mixture of Experts（MoE，混合专家）不是“把多个模型拼在一起”，也不只是“用 Router 选择专家”。
> 它要解决的核心问题是：**模型希望拥有更大的参数容量，但硬件无法为每个 token 激活全部参数。**
> MoE 通过条件计算，让不同 token 只经过少量参数子集，从而解除“总参数量必须近似等于单 token 计算量”的绑定。
>
> 本文承接 [`decoder_only_architecture.md`](decoder_only_architecture.md) 中的 FFN 部分，按照
> **第一性原理降维 → 高阶结构化类比 → 边界与反模式 → 动机演进与语义压缩**四步展开。
> 重点不是记忆 Router、Top-K、EP 等名词，而是理解它们分别在修补哪一个不可消失的底层矛盾。

## 1. 第一性原理降维：MoE 究竟在解哪条约束

### 1.1 从 Decoder Block 中定位 MoE

标准 decoder-only Transformer 的每一层通常包含两个主要子层：

```text
hidden states
     │
     ├──► Attention ──► 残差相加
     │
     └──► FFN       ──► 残差相加
```

MoE 一般不替换 Attention，而是把原来的单个稠密 FFN 替换为多个并列 FFN：

```text
Dense FFN:

x ──► FFN ──► y

Sparse MoE FFN:

                          ┌──► Expert 0 ──┐
                          ├──► Expert 1 ──┤
x ──► Router ──► Top-K ──┼──►    ...     ├──► 加权合并 ──► y
                          └──► Expert E-1 ─┘
                       每个 token 只进入 K 个专家
```

设输入为：

$$
X \in \mathbb{R}^{T \times d_{\text{model}}}
$$

其中：

| 符号 | 含义 |
|---|---|
| $T$ | 当前设备或当前批次中的 token 数 |
| $d_{\text{model}}$ | Transformer 隐藏维度 |
| $d_{\text{ff}}$ | 一个 FFN 的中间维度 |
| $E$ | 专家总数 |
| $K$ | 每个 token 激活的专家数，通常 $K \ll E$ |

每个专家本质上是一个独立 FFN。以 SwiGLU 为例：

$$
\operatorname{Expert}_e(x)
=
W_{e,\text{down}}
\left(
\operatorname{SiLU}(W_{e,\text{gate}}x)
\odot
W_{e,\text{up}}x
\right)
$$

因此，“专家”不是一种新的神经网络基本算子；它通常只是**参数彼此独立的 FFN 实例**。

### 1.2 不可再降维的核心矛盾：容量与激活成本耦合

对一个稠密 FFN，忽略 bias 和常数项，其参数量与单 token 计算量都近似为：

$$
P_{\text{dense}} = \Theta(d_{\text{model}}d_{\text{ff}})
$$

$$
C_{\text{dense/token}} = \Theta(d_{\text{model}}d_{\text{ff}})
$$

这意味着稠密网络存在一个刚性绑定：

$$
\text{增加可学习参数容量}
\Longrightarrow
\text{几乎同比增加每个 token 的计算量}
$$

如果直接把 FFN 中间维扩大 $E$ 倍，那么参数容量和单 token FLOPs 都扩大约 $E$ 倍。模型容量需要更多参数，硬件吞吐却要求每个 token 少做计算，这就是 MoE 出现前无法同时满足的目标。

MoE 引入 $E$ 个专家，但每个 token 只激活其中 $K$ 个：

$$
P_{\text{MoE}} \approx E P_{\text{expert}}
$$

$$
C_{\text{MoE/token}} \approx K C_{\text{expert}} + C_{\text{router}}
$$

当 $K \ll E$ 时：

$$
\frac{P_{\text{MoE}}}{P_{\text{expert}}}=E,
\qquad
\frac{C_{\text{MoE/token}}}{C_{\text{expert}}}\approx K
$$

例如 $E=64$、$K=2$：模型可以持有约 64 份专家参数，但一个 token 只执行约 2 份专家计算。MoE 真正拆开的不是“模型”和“专家”，而是：

$$
\boxed{\text{总参数容量} \neq \text{单 token 激活参数量}}
$$

### 1.3 条件计算的最小数学结构

Router 为 token $x_t$ 计算专家 logits：

$$
z_t = W_r x_t,
\qquad
z_t \in \mathbb{R}^{E}
$$

经过 softmax 得到路由概率：

$$
p_{t,e}
=
\frac{\exp(z_{t,e})}
{\sum_{j=1}^{E}\exp(z_{t,j})}
$$

再选出概率最大的 $K$ 个专家：

$$
S_t = \operatorname{TopK}(p_t, K)
$$

最终输出为：

$$
y_t
=
\sum_{e \in S_t}
\alpha_{t,e}\operatorname{Expert}_e(x_t)
$$

其中 $\alpha_{t,e}$ 是被选中专家的权重。常见选择包括：

1. 保留全体专家 softmax 中对应项，此时通常有

$$
\sum_{e \in S_t}\alpha_{t,e} \le 1
$$

2. 在 Top-K 内重新归一化：

$$
\alpha_{t,e}
=
\frac{p_{t,e}}
{\sum_{j \in S_t}p_{t,j}}
$$

Router 的本质不是“理解 token 属于哪个领域”，而是在当前参数状态下求解一个离散资源分配问题：

$$
\text{token} \longrightarrow \text{少量可执行参数块}
$$

“专家是否形成语义专门化”是训练后的涌现结果，而不是 Router 接口本身保证的性质。

### 1.4 MoE 没有消灭成本，只是改变了成本形态

条件计算降低了每个 token 的**算术激活量**，但所有专家参数仍然必须被存储，且 token 必须被送往对应专家。因此成本从单一 GEMM 转化为四部分：

$$
T_{\text{MoE}}
=
T_{\text{route}}
+
T_{\text{dispatch}}
+
T_{\text{expert}}
+
T_{\text{combine}}
$$

| 成本 | 来源 | 主要硬件瓶颈 |
|---|---|---|
| Router | 计算专家分数并做 Top-K | 小矩阵、归约、排序 |
| Dispatch | 按专家重排或跨设备发送 token | HBM 带宽、互联带宽、同步 |
| Expert | 对每个专家执行分组 GEMM | Tensor Core 利用率、批量大小 |
| Combine | 把专家输出送回原 token 顺序并加权 | 通信、scatter/reduce |

这揭示第一个物理限制：**参数可以稀疏激活，但数据必须被移动到参数所在的位置，或参数被移动到数据所在的位置。两者至少发生一个。**

在 Expert Parallelism（EP，专家并行）中，通常选择固定专家、移动 token。若专家分布在不同 GPU，dispatch/combine 常需要 All-to-All（全互换）通信。

### 1.5 第二个物理限制：动态稀疏会破坏规则计算

稠密 FFN 可以把所有 token 放进一个大 GEMM：

$$
[T,d_{\text{model}}]
\times
[d_{\text{model}},d_{\text{ff}}]
$$

MoE 路由后，第 $e$ 个专家收到的 token 数为：

$$
N_e = \sum_{t=1}^{T}\mathbf{1}[e \in S_t]
$$

专家计算变成一组大小不一的 GEMM：

$$
[N_e,d_{\text{model}}]
\times
[d_{\text{model}},d_{\text{ff}}],
\qquad e=1,\ldots,E
$$

理论总计算量下降，不代表实际延迟同比下降。若 $N_e$ 很小或极不均衡，硬件会面临：

- 小 GEMM 无法充分占满 Tensor Core；
- 热门专家排队，冷门专家空闲；
- padding 到统一容量会计算无效 token；
- 动态形状增加调度与 kernel launch 开销。

所以 MoE 的真实性能约束不是平均负载，而是最慢专家：

$$
T_{\text{step}}
\gtrsim
\max_e T_{\text{expert}}(N_e)
$$

即使平均值满足：

$$
\mathbb{E}[N_e] = \frac{TK}{E}
$$

也不能推出尾部负载足够小。MoE 的核心工程问题因此不是“怎样算 Top-K”，而是：

$$
\boxed{\text{怎样在保持选择性的同时，让不规则选择仍可被规则硬件高效执行}}
$$

### 1.6 第三个物理限制：容量上限与信息损失

训练系统常为每个专家设置容量：

$$
C
=
\left\lceil
\gamma \frac{TK}{E}
\right\rceil
$$

其中 $\gamma$ 是 capacity factor。若某专家收到的 token 数 $N_e>C$，系统必须选择：

- 丢弃超额 token；
- 把 token 路由到次选专家；
- 动态扩容，接受不规则内存与延迟；
- 增加冗余专家或复制热门专家。

容量因子体现了一个无法绕过的三角约束：

| 目标 | 代价 |
|---|---|
| 不丢 token | 接受更高容量或动态形状 |
| 不浪费计算 | 接受溢出或负载尾延迟 |
| 固定执行时间 | 接受 padding 或路由约束 |

MoE 并没有让计算资源无限可分；它只是让模型能在固定资源预算内进行更细粒度的取舍。

## 2. 高阶结构化类比：MoE 与分片数据库查询优化器

简单地把专家类比为“不同科室医生”只能解释分工，无法解释路由、倾斜、通信和尾延迟。更接近 MoE 拓扑结构的是：**分片数据库 + 查询优化器 + 分布式执行引擎**。

### 2.1 结构映射

| MoE 系统 | 分片数据库 | 共同结构 |
|---|---|---|
| token | 一条查询或一批记录 | 待处理的数据单元 |
| Router | 查询优化器/分片路由器 | 根据输入选择执行节点 |
| Expert | 数据分片上的执行算子 | 拥有独立状态与计算能力 |
| Top-K | 选择少量候选分片 | 避免扫描全部节点 |
| Dispatch | shuffle/exchange | 把数据发送到状态所在位置 |
| Expert Parallelism | 水平分片 | 不同设备持有不同参数分片 |
| Combine | 汇总局部查询结果 | 恢复原顺序并合并结果 |
| 负载均衡损失 | 数据倾斜治理 | 防止热点集中到少数节点 |
| capacity factor | 分片队列/并发上限 | 限制单节点最坏负载 |

两者都在执行同一个抽象过程：

$$
\text{输入}
\xrightarrow{\text{选择位置}}
\text{移动数据}
\xrightarrow{\text{局部计算}}
\text{汇总结果}
$$

### 2.2 为什么这个类比比“专家团队”更准确

#### 2.2.1 选择性与局部状态

数据库不把每条查询广播给所有分片，因为全量扫描会让节点数增加却不降低单查询成本。MoE 同理：如果每个 token 都执行所有专家，系统就退化为超宽稠密 FFN。

二者的收益都来自：

$$
\text{全局状态很多，但单次请求只访问少量局部状态}
$$

#### 2.2.2 数据倾斜决定尾延迟

假设 64 个分片平均各处理 100 条记录，但一个热点分片收到 2000 条。查询完成时间不由平均 100 决定，而由热点分片决定。MoE 中专家负载也满足相同的 barrier 结构：所有专家结果返回后才能继续下一层，因此一个热点专家足以拖慢整个批次。

#### 2.2.3 Shuffle 可能比计算更贵

分布式数据库中，连接或聚合前的 shuffle 经常成为瓶颈；MoE 中跨 GPU dispatch/combine 也可能超过专家 GEMM 本身。若每个 token 携带 $d_{\text{model}}$ 个元素，粗略通信量与下式成正比：

$$
V_{\text{dispatch}}
\propto
T K d_{\text{model}}
$$

返回专家输出还需要一次反向数据交换，因此总流量近似包含两次 token 搬运。增加专家数不会自动增加计算通信比；如果本地 token 太少，系统反而从计算受限转为通信受限。

#### 2.2.4 优化器正确不等于执行器高效

数据库优化器即使选中了逻辑上最相关的分片，也可能因为热点、网络或统计信息过时而执行缓慢。MoE Router 即使提高了模型损失意义下的选择质量，也可能制造极差的设备负载。

因此 Router 同时承担两个目标：

$$
\min \mathcal{L}_{\text{task}}
$$

以及

$$
\min \mathcal{L}_{\text{balance}}
$$

二者可能冲突：最优语义路由可能天然偏向少数专家，最均匀路由又可能破坏专家专门化。

### 2.3 从数据库类比推导 MoE 的完整执行流水线

设有 8 个专家、2 张 GPU，每张 GPU 放 4 个专家；每个 token 选择 Top-2。

```text
原始 token 顺序
[t0, t1, t2, t3]
        │
        ▼ Router
 t0 -> {E1, E6}
 t1 -> {E0, E2}
 t2 -> {E6, E7}
 t3 -> {E1, E6}
        │
        ▼ 按目标专家分桶
 GPU 0: E0:[t1], E1:[t0,t3], E2:[t1], E3:[]
 GPU 1: E4:[],   E5:[],      E6:[t0,t2,t3], E7:[t2]
        │
        ▼ All-to-All / 本地重排
 每张 GPU 收到本地专家需要的 token
        │
        ▼ Grouped GEMM
 不同专家用各自参数处理各自 token
        │
        ▼ 反向 All-to-All + 按 token 还原
 t0 <- α01·E1(t0) + α06·E6(t0)
 t1 <- α10·E0(t1) + α12·E2(t1)
 t2 <- α26·E6(t2) + α27·E7(t2)
 t3 <- α31·E1(t3) + α36·E6(t3)
```

这个过程与分片数据库的“路由—exchange—局部算子—gather”同构。它也说明：Top-K 只是选择阶段，远不是 MoE 执行的全部。

### 2.4 类比的边界

MoE 与分片数据库并不完全相同：

- 数据库分片规则通常由 key 或元数据确定；MoE Router 参数会随训练更新。
- 数据库追求精确查询语义；MoE 的路由是可学习近似，专家之间可以冗余。
- 数据库热点通常是外生数据分布造成的；MoE 热点还会被梯度反馈进一步强化。
- MoE 的专家输出参与连续可微计算，但 Top-K 选择本身具有离散性。

这个类比用于解释执行拓扑与资源矛盾，不应被误解为 MoE 就是一套数据库系统。

## 3. 边界与对立面：MoE 不是什么

### 3.1 与邻近方案的本质分界线

| 方案 | 参数是否分支 | 单 token 是否只激活子集 | 选择是否依赖当前 token | 核心目的 |
|---|---:|---:|---:|---|
| 稠密 FFN | 否 | 否 | 否 | 规则、稳定的全参数计算 |
| 宽稠密 FFN | 否 | 否 | 否 | 用更多计算换容量 |
| Sparse MoE | 是 | 是 | 是 | 解耦总容量与激活计算量 |
| Ensemble | 是 | 通常否 | 通常否 | 多模型结果融合，提高鲁棒性 |
| Adapter/LoRA | 是 | 可能 | 通常由任务固定 | 低成本适配已有模型 |
| 结构化剪枝 | 否或静态分块 | 是 | 否 | 永久删除低价值参数 |
| 动态深度/早退 | 按层选择 | 是 | 是 | 减少执行层数，而非 FFN 专家选择 |
| Expert Parallelism | 是 | 取决于上层 MoE | 否 | 把专家参数放到多设备，不定义路由语义 |

最关键的分界线是：

$$
\boxed{\text{MoE 是输入相关的参数激活；静态切分只是参数放置}}
$$

EP 经常与 MoE 同时出现，但两者不是同义词：

- MoE 回答“一个 token 应计算哪些专家”；
- EP 回答“这些专家参数存在哪些设备上”。

没有 EP，多个专家可以全部放在同一张 GPU；没有稀疏 MoE，也可以把稠密权重做张量并行切分。

### 3.2 MoE 与 Attention 的边界

Attention 和 MoE 都包含“打分—选择/加权—聚合”，但它们选择的对象不同：

| 维度 | Attention | MoE Router |
|---|---|---|
| 被选择对象 | 其他 token 的动态表示 | 专家参数块 |
| 主要作用 | token 间信息混合 | 为 token 选择计算路径 |
| 状态来源 | 当前序列的 K/V | 训练得到的专家权重 |
| 输出 | 其他 token value 的加权和 | 专家 FFN 输出的加权和 |
| 主要扩展瓶颈 | 序列长度、KV Cache | 参数存储、负载均衡、All-to-All |

Attention 决定“从哪些 token 读取信息”，MoE 决定“用哪些参数处理信息”。二者都可稀疏化，但稀疏的轴不同。

### 3.3 极限边界与退化情形

#### 情形 A：$K=E$

每个 token 激活全部专家：

$$
y_t = \sum_{e=1}^{E}\alpha_{t,e}\operatorname{Expert}_e(x_t)
$$

此时失去稀疏计算优势，退化为稠密专家混合。参数容量与单 token 计算量重新绑定。

#### 情形 B：$E=1$、$K=1$

只有一个专家，Router 没有选择空间，系统退化为普通 FFN。

#### 情形 C：$K=1$

每个 token 只走一个专家，计算最省、合并最简单，但路由错误无法由第二专家缓冲，Top-1 决策也更容易产生不连续和负载热点。

#### 情形 D：$E$ 极大而 batch 极小

若平均每个专家收到的 token 数：

$$
\frac{TK}{E} \ll 1
$$

多数专家为空，少数专家只执行极小 GEMM。理论 FLOPs 很低，实际 GPU 利用率和通信效率却可能极差。Decode 阶段尤其容易落入该区域。

#### 情形 E：Router 完全均匀

如果所有专家概率始终相同，Top-K 的选择可能由索引顺序或微小数值噪声决定。负载或许均匀，但专家没有稳定分工，额外参数容量未被有效利用。

#### 情形 F：Router 完全塌缩

若所有 token 都选择同一批专家：

$$
N_{e^*} \approx TK,
\qquad
N_{e\neq e^*}\approx 0
$$

系统在统计上仍有许多专家，实际上却退化为少数专家模型，并产生最严重的负载倾斜。

### 3.4 典型反模式

#### 反模式 1：只看理论 FLOPs，不看 token 搬运

错误推理：Top-2 只执行两个专家，所以一定比稠密 FFN 快。

问题：Router、Top-K、permute、All-to-All、unpermute 都不是免费的。小 batch 或慢互联下：

$$
T_{\text{communication}} + T_{\text{routing}}
>
T_{\text{saved GEMM}}
$$

此时参数更多、系统更复杂，延迟却更高。

#### 反模式 2：把专家数量当成可无限扩展的免费容量

增加 $E$ 会增加：

- 权重显存与加载时间；
- 跨设备放置复杂度；
- 小 GEMM 和空专家比例；
- Router 输出维度与 Top-K 成本；
- 故障域和分布式同步复杂度。

当 $TK/E$ 过小时，更多专家不是容量红利，而是碎片化。

#### 反模式 3：强迫绝对均匀，破坏可学习专门化

负载均衡是资源约束，不是模型最终目标。若均衡正则过强，Router 会优先满足“每个专家一样忙”，而不是“为 token 选择最合适的参数”。

优化目标应理解为受约束问题：

$$
\min \mathcal{L}_{\text{task}}
\quad
\text{s.t.}
\quad
N_e \le C
$$

而不是把均匀本身当作模型质量。

#### 反模式 4：训练路由与推理执行假设不一致

训练时使用大 token batch，专家负载相对平滑；在线 decode 时每步 token 很少，路由方差和小 GEMM 问题会显著放大。如果仅以训练吞吐判断部署效果，可能得到无法高效服务的模型。

#### 反模式 5：把 Top-K 概率直接等同于专家能力解释

Router 高分只说明当前联合训练系统倾向于选择该专家，不证明它具有人类可命名的领域能力。专家可能按语法位置、频率、表示空间方向或硬件均衡要求分工，而不是按“数学专家”“代码专家”等显式类别分工。

#### 反模式 6：忽视确定性和数值边界

当多个专家 logits 非常接近时，微小浮点误差可能改变 Top-K 顺序。选择一旦改变，后续执行的是完全不同的一组参数，误差不再只是连续数值扰动，而会变成离散路径变化。对严格可复现推理，Router kernel、排序稳定性和并行归约顺序都需要单独约束。

### 3.5 什么时候不应该使用 MoE

以下场景中，稠密 FFN 可能更合理：

- 模型足够小，参数容量不是主要瓶颈；
- 极低延迟、极小 batch，路由和通信开销无法摊薄；
- 设备互联慢，无法支撑频繁 All-to-All；
- 部署环境显存有限，无法容纳总专家参数；
- 强调实现简单、确定性和跨硬件可移植性；
- token 数不足以让每个专家形成高效 GEMM。

MoE 优化的是“容量受限但单 token 计算预算固定”的区域，并不是 FFN 的无条件替代品。

## 4. 语义压缩与动机演进：从稠密 FFN 到稀疏专家系统

### 4.1 在 MoE 之前：扩大模型意味着扩大每次计算

早期稠密网络遵循隐含假设：

$$
\text{一个样本应经过模型的全部参数}
$$

在这一假设下，增加能力通常依赖：

- 加深网络；
- 加宽隐藏层；
- 增大 FFN 中间维；
- 增加 Attention 头或通道。

共同结果是总参数和每样本计算同步增长。硬件利用率很规则，但扩展路径被 FLOPs 锁死。

### 4.2 第一次假设翻转：不同输入不必使用相同参数

MoE 推翻的第一个假设是：

> 所有 token 必须经过同一套 FFN 参数。

如果不同输入只需要模型能力空间中的一小部分，那么可以把参数划为多个子网络，并让输入选择路径。这把“网络结构固定”改为“执行图由输入决定”。

其收益来自条件性：

$$
\text{大量可选参数}
+
\text{少量实际激活参数}
$$

没有“少量激活”，多专家只是昂贵的 ensemble；没有“大量可选”，稀疏激活也没有容量收益。

### 4.3 第二次假设翻转：计算稀疏不等于存储稀疏

MoE 接受了一个新的交换：

- 用更多存储容纳全部专家；
- 用更少算术执行单个 token；
- 用路由和通信连接二者。

因此 MoE 更适合“算力预算比参数存储预算更紧”的扩展目标。它不是全面降本，而是把成本从每 token FLOPs 转移到：

$$
\text{显存容量} + \text{通信} + \text{调度复杂度}
$$

这解释了为什么 MoE 模型总参数可以很大，却不能简单称为“与同参数稠密模型一样昂贵”；也不能简单称为“只等于激活参数规模”，因为未激活参数仍需存储、加载和分布式管理。

### 4.4 第三次演进：从理论稀疏走向硬件可执行稀疏

最初的条件计算关注“少算哪些参数”，现代 MoE 系统还必须回答“如何让 GPU 高效执行不规则选择”。于是逐步出现：

1. **Top-K Router**：把任意稀疏门控限制成固定小 $K$，控制计算上界；
2. **容量因子**：把动态专家负载约束到可预分配缓冲区；
3. **负载均衡损失**：在训练目标中加入硬件可执行性偏好；
4. **Token permutation**：把同一专家的 token 排到一起，恢复连续矩阵计算；
5. **Grouped GEMM**：一次调度多个不同规模的专家 GEMM；
6. **Expert Parallelism**：将总专家参数分散到多设备；
7. **All-to-All 融合与重叠**：隐藏 token 搬运延迟；
8. **专家复制与动态负载均衡**：缓解运行时热点。

演进方向不是让路由越来越复杂，而是让动态模型重新适配静态吞吐机器。

### 4.5 训练与推理的目标错位

训练阶段关心：

- 梯度能否到达 Router 和专家；
- 专家是否塌缩；
- token 是否因容量溢出被丢弃；
- 大规模并行吞吐是否稳定。

推理阶段关心：

- 权重能否放入设备；
- prefill 和 decode 的 token 规模差异；
- All-to-All 尾延迟；
- 小 batch 下专家 GEMM 利用率；
- 路由是否确定；
- 热门专家是否造成服务抖动。

因此“训练成功的 MoE”不自动等于“可高效服务的 MoE”。从训练到推理，需要把模型学到的动态稀疏映射为具体的 rank、设备、缓冲区和通信计划。

### 4.6 MoE 的价值与代价总表

| 维度 | 稠密 FFN | Sparse MoE |
|---|---|---|
| 总参数容量 | 与单 token 计算强耦合 | 可显著大于激活参数量 |
| 单 token 计算 | 执行全部 FFN 参数 | 只执行 $K$ 个专家 |
| 权重存储 | 相对较少 | 必须保存全部专家 |
| 执行形状 | 大而规则的 GEMM | 动态分桶后的多个 GEMM |
| 通信 | TP 等规则集合通信 | 常含 token All-to-All |
| 负载 | 基本静态 | 输入相关，可能倾斜 |
| 硬件利用率 | 易于优化 | 依赖每专家 token 数 |
| 模型容量扩展 | 增容通常增算 | 可在近似固定激活计算下增容 |
| 实现复杂度 | 较低 | Router、调度、通信、均衡共同决定性能 |
| 最坏风险 | 算力不足 | 专家塌缩、热点、通信吞噬收益 |

### 4.7 一句话高倍率压缩

> **MoE 的本质，是让每份输入只唤醒庞大参数库中的少数部分，以数据搬运和调度复杂度换取“模型知道得更多，但每次不必把所有知识都算一遍”。**
