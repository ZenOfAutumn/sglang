# Anthropic 反蒸馏具体策略：基于原文的总结

> **主要来源**：本地原始 PDF《Detecting and countering misuse of AI: September 2026》，封面标注发布日期为 2026 年 9 月 10 日。[1]
> **重点范围**：第 153–154 页 “How we address illicit distillation”；第 143–152 页用于解释攻击背景与防御局限。文中页码与 PDF 页码一致。
> **整理日期**：2026 年 9 月 13 日。
> **证据边界**：本文总结报告自身披露，不代表对其企业归因、攻击规模或防御效果进行了独立验证。本次在线检索未取得可核对的官方正文，因此以仓库内 PDF 为依据，不声称已验证其与线上版本一致。

## 一、核心结论

**Anthropic 披露的不是一种“让模型无法被蒸馏”的算法，而是一组分层措施：识别并切断规模化访问、检测并拦截推理提取、降低输出的训练价值，以及限制隐藏推理在被修改的上下文中重放。**[1，pp.153–154]

报告明确区分正常蒸馏与其所称的“非法蒸馏”：后者指未经授权、工业规模、隐蔽地提取并复制模型能力的行动，通常涉及欺诈账号、被盗凭证或代理网络。因此，不能把以下措施理解为对一切蒸馏活动的禁止。[1，p.143]

## 二、具体策略总览

下表的“作用”是对原文机制的归纳，不是报告公布的量化效果。

| 层次 | 原文披露的措施 | 具体作用 | 原文位置 |
| --- | --- | --- | --- |
| 访问与组织层 | 利用元数据和异常活动信号识别代理账号网络，并归因到组织 | 不只处理单个账号，而是针对关联组织采取综合处置 | p.153 |
| 请求检测层 | 部署专门检测对抗性提取的分类器 | 在高置信度确认相关请求属于非法蒸馏或其他未授权使用后，拦截请求并封禁关联账号 | p.153 |
| 输出层 | 返回前对内部推理进行摘要 | 降低被收集的推理文本作为其他模型训练数据的价值 | p.153 |
| 隐藏推理层 | 用 `thinking signature` 引用原始推理，而非直接暴露原始推理 | 减少直接获得完整思维链的机会，但报告也披露了绕过案例 | pp.148–150、153 |
| 上下文完整性层 | Fable 5.1 的 Preserved Thinking 限制修改推理之前的上下文 | 针对“保留隐藏推理、替换前置指令、诱导泄露”的攻击 | p.153 |
| 身份与准入层 | 对存在潜在滥用信号的账号要求身份验证 | 未通过验证的账号被封禁，限制未授权转售和不受支持地区的访问 | pp.153–154 |
| 持续改进 | 将调查和处置所得用于后续防护 | 根据攻击手法变化更新措施 | p.154 |

这些是不同控制点，并非报告声称相互独立的七套产品。尤其是推理摘要、签名引用与上下文保护，需要结合起来理解。

## 三、逐项解释

### 1. 从单个账号封禁升级到代理网络和组织级处置

**原文披露**：通过元数据和异常活动信号识别代理服务网络关联账号，进一步将可疑活动归因到具体组织，再采取综合处置，而不是逐个封禁代理账号。[1，p.153]

**为什么需要这样做**：报告描述，攻击方会使用大规模账号池，单个账号池被封禁后还能迅速切换；同一代理网络也可能为不同组织提供访问。[1，pp.144、148]

**机制解读**：关注点从“这个账号是否异常”扩展到“这些账号是否共同支撑同一场提取行动”，以应对多账号分摊和账号池切换。

**未披露的细节**：

- 使用哪些元数据字段，如何组合异常信号；
- 是否采用图关联、设备指纹或支付关联算法；
- 组织归因的阈值、误判率及具体处置范围。

因此，不能把常见风控工程做法直接写成 Anthropic 已部署的实现。

### 2. 对抗性提取专用分类器：识别请求，拦截并封号

**原文披露**：Anthropic 构建了专门用于检测对抗性提取的分类器，并在 Fable 5 发布时强化；当其有把握认定一组请求与非法蒸馏行动或其他未授权使用有关时，会阻断请求并封禁关联账号。[1，p.153]

报告给出的攻击背景包括伪装成调试、伪造系统指令、借翻译任务提取先前推理，以及大批量测试提取提示。[1，pp.145–146]

**机制解读**：被提取的内容即使是正常编程或数学推理，也可能因提取行为本身而触发反蒸馏检测。这与只判断答案内容是否危险的安全过滤不是同一个问题。

**边界**：

- 原文没有公布分类器架构、训练数据、部署位置或具体决策阈值。
- 原文没有证明它覆盖全部提取方式。
- 报告称一次超过 12,000 个请求的技术筛选中，大多数提取尝试被拒绝，但部分成功并被用于更大规模攻击；不能将这段描述换算成正式检测率或视为当前版本的评测结果。[1，p.145]

### 3. 推理摘要：降低可获取训练数据的价值

**原文披露**：Claude 在回复前对内部推理做摘要，使被窃取的转写文本更难用于训练其他模型。[1，p.153]

**机制解读**：完整推理可能提供更多中间步骤与解题过程；摘要减少直接对外提供的细节，目标是降低数据价值，而不是阻止所有输出被收集。

**必须区分**：

- 摘要不等于不返回答案，也不等于彻底消除蒸馏价值。
- 报告没有说模型停止产生内部推理。
- 报告没有披露摘要保留比例、摘要生成方式，或采用摘要后蒸馏收益下降多少。
- 如果原始推理仍可被重放并诱导输出，摘要这一层就可能被绕过；报告明确描述了此类案例。[1，pp.148–150]

### 4. 隐藏推理与签名引用：防止直接读取，但不是完整的防重放措施

**原文披露**：Claude 返回指向原始思考的 `thinking signature`，由 API 在后续调用中用来查找原始推理；报告第 153 页另明确表示推理受到加密保护。[1，pp.148、153]

**防御目的**：客户端不必直接获得完整明文推理，也能继续使用多轮推理上下文。

**报告同时披露的局限**：攻击方保存签名，在新会话中重放，并诱导 Claude 将隐藏推理输出为完整文本，从而绕过这一控制。[1，pp.148–150]

**关键区别**：让客户端无法直接读懂隐藏推理，与限制服务端在什么上下文下使用该推理，是两个不同问题。报告中的绕过不构成底层加密算法被破解的证据。

本报告未详细披露签名的数据结构、密码算法、密钥管理或服务端存储实现，不应仅凭“引用”或“加密”就断言其完整架构。

### 5. Preserved Thinking：限制修改隐藏推理之前的上下文

**原文披露**：Fable 5.1 引入 Preserved Thinking，阻止新 API 账号在多轮对话中修改位于 Claude 推理之前的系统提示词、工具或消息。报告解释，修改这些前置上下文是诱导模型泄露加密推理的常见手段。[1，p.153]

**它针对的攻击关系**：

1. 在一组正常指令下产生隐藏推理。
2. 保留该推理的签名或载荷，但改变它之前的指令或消息。
3. 利用改变后的上下文诱导模型披露已有推理。

**机制解读**：保护对象不只是推理块本身，还包括它产生时的前置上下文。这样可以限制“推理来自原任务，但解释和使用推理的指令已被替换”的情况。

**原文适用边界**：

- 第 153 页明确提到的是 **Fable 5.1 和新 API 账号**，不能扩大为所有模型、所有历史账号已统一强制执行。
- 限制的是推理之前的历史上下文变更，不能概括成“禁止继续对话”或“禁止追加消息”。
- 该段没有说明其是否绑定账号、租户或会话 ID，也没有说明能否阻止所有跨账号、跨模型重放。
- 该段没有公布错误码、失败后的回退策略或具体绑定算法。

仓库另有《Claude-Preserved-Thinking-官方文档.md》记录更细的 API 行为。[2] 那些细节属于另一份材料，不能反向当作本报告第 153 页已经披露的内容；详见文末独立技术附录。

### 6. 风险触发的身份验证与访问撤销

**原文披露**：发现潜在滥用信号时，例如未授权转售 Claude，或账号从中国、俄罗斯、伊朗等不受支持国家运行，系统可以要求用户验证身份以保留访问权限；未通过的账号会被封禁。[1，pp.153–154]

**机制解读**：除了分析请求内容，还通过身份和访问资格限制代理网络及未授权使用。

**边界**：

- 原文是“检测到风险信号后可以要求验证”，不是“所有用户每次请求都必须验证”。
- 国家或地区是访问规则的例子，不等于仅凭语言、姓名或国籍认定蒸馏。
- 原文未披露具体证件要求、验证供应商、申诉流程或风控阈值。

### 7. 将调查结果反馈到防护

**原文披露**：对蒸馏攻击的调查和处置所得，将继续用于改进防护。[1，p.154]

**机制解读**：组织归因、分类器和其他保护措施需要随着提取手法变化持续更新。报告没有披露更新频率、自动化程度或内部处理流程。

## 四、相关措施：领域安全防护也能限制特定能力提取

报告称，在一起针对网络能力的蒸馏行动中，Fable 更强的网络安全防护削弱了攻击，攻击者随后转向其认为防护较弱的模型。[1，p.151]

这说明领域安全防护可能限制特定危险能力的提取，但它应与“反蒸馏专用分类器”分开看待：前者限制某类能力的输出，后者针对未授权提取行为。

该案例是报告方的观察，不足以证明所有模型上的网络能力蒸馏均被阻止，也不构成全平台防御成功率。

## 五、原文没有支持哪些结论

以下技术可以出现在反蒸馏研究或工程方案中，但**本报告反蒸馏章节没有披露 Anthropic 已采用它们**：

- 给输出加入水印、指纹或可追踪标记；
- 故意返回错误答案、投毒样本，或主动破坏攻击者的训练数据；
- 使用差分隐私，或专门修改权重以实现抗蒸馏；
- 使用某一种 AEAD、Merkle 树、密钥轮换或服务端状态存储方案；
- 采用确定的速率限制、账号配额或相似度阈值；
- 已全面阻止跨用户、跨会话、跨模型的所有推理重放；
- 已通过公开实验量化各防护层对最终学生模型能力的影响。

尤其不要把《Stealing Reasoning Traces from Proprietary LLM APIs》论文中的防御建议，混写成 Anthropic 这份报告宣布已经落地的措施。

## 六、总结

可以将原文策略归纳为四个目标：

1. **限制访问**：代理网络识别、组织级处置、风险触发的身份验证。
2. **阻断提取**：专用分类器、请求拦截及关联账号封禁。
3. **降低收益**：提供推理摘要，减少完整原始推理的直接暴露。
4. **限制重放**：保护推理产生时的前置上下文，降低通过上下文修改诱导泄露的机会。

最重要的技术认识是：**隐藏或加密推理本身不够，还需要限制其被重新使用的上下文。**不过，原文没有给出“彻底防止蒸馏”的保证，也没有提供可独立复现的整体效果评测。[1，pp.148–154]

## 技术附录：Preserved Thinking 如何限制推理重放

> **本附录来源不同于正文**：以下按仓库保存的 Preserved Thinking 中文文档整理，引用其章节名定位。[2] 本次打开该文档标注的官方页面未获得可核对正文，因此模型名、日期、参数与 Beta Header 均仅代表本地材料记录，**不是已验证的当前 API 契约**。没有执行真实 API 测试。

### A. 三类校验，而非仅校验密文有没有被修改

本地文档“工作原理”描述了三类检查：[2，“工作原理”]

| 检查 | 本地文档描述 | 对防御的意义（解读） |
| --- | --- | --- |
| 模型兼容性 | 推理块可由生成它的模型及后续更新模型读取，较早模型不能读取；具体以模型兼容列表为准 | 限制新模型推理被交给不兼容旧模型处理 |
| 前置上下文 | 检查顶层 `system`、参与绑定的 `tools` 及思考块之前的消息是否保持不变 | 限制保留推理、替换前置指令的重放 |
| 思考块链条 | 跨轮次记录更早的思考块；从中间删除一个块，会使其后思考块失效 | 限制对推理历史的选择性删改 |

这里有三个容易遗漏的限定：

- **“更新模型”不等于“参数更多”或“防护一定更强”**。本地文档没有把兼容规则定义为按模型大小排序，也未在该文件列出完整兼容矩阵。
- **思考链与普通前缀分开处理**。更早的 `thinking`、`redacted_thinking` 块不属于普通前缀，而是通过思考链检查；文档允许从历史开头连续移除思考块，不允许在保留后续思考的同时任意挖掉中间块。
- **规则存在明确例外**。例如尚未被引用的延迟加载工具不属于绑定前缀；服务端压缩后，检查的前缀从最近压缩块开始。因此不能用“整个请求 JSON 必须逐字节相同”概括。

这更接近“推理只能在兼容的使用环境中继续生效”，而不是禁止保存、恢复或正常分叉会话。[2，“工作原理”“哪些操作属于编辑”“常见问题”]

### B. 失败处理：拒绝请求，或者继续但不使用失效推理

本地文档用 `thinking.block_binding.prefix_mismatch_behavior` 控制**前缀不匹配**时的处理，记录的 Beta Header 为 `thinking-binding-controls-2026-08-01`。[2，“工作原理”]

| 情况 | 本地文档记录的处理 | 容易误解之处 |
| --- | --- | --- |
| 前缀不匹配，设置 `"error"` | 返回 400 `invalid_request_error`，指出首个失败块 | 原样重试不能修复上下文不匹配 |
| 前缀不匹配，设置 `"drop_block"` | 移除失效块及之后的思考块，请求继续 | 不是放宽绑定让旧推理继续可用，而是不把失效推理交给模型 |
| 模型不兼容 | 不兼容的思考块在该请求中被丢弃 | 不由 `prefix_mismatch_behavior` 决定 |
| Message Batches API 未设置该字段 | 文档另列例外：默认丢弃失败块；要报错需显式设 `"error"` | 不能将普通请求的默认报错行为推广到所有接口 |

开启相应 Header 后，可以从 `input_transformations` 观察丢弃行为。文档列举两个原因：`prefix_binding_mismatch` 和 `model_binding_mismatch`；流式响应在 `message_start` 事件中提供相关信息。[2，“如何判断你的集成是否受影响”“决定发生不匹配时如何处理”]

**安全含义**：`drop_block` 保留的是请求可继续执行的能力，不是失效推理的可用性。它不是一种“关闭反蒸馏校验”的开关。

### C. 哪些日常 Agent 操作会受影响

下表是对本地文档迁移说明的摘记，不是已验证适用于所有 Claude 模型的通用接入建议。[2，“哪些操作属于编辑”“更新你的集成”]

| 常见操作 | 影响或风险 | 文档给出的处理方向 |
| --- | --- | --- |
| 每轮向顶层 `system` 写入新时间、预算或模式 | 改变已有思考的前缀 | 固定初始系统提示；通过追加的会话中途消息传入变化 |
| 更新 `AGENTS.md` 后重新渲染历史指令 | 覆盖推理生成时的历史内容 | 追加新版本；不可信文件内容不要提升为系统指令 |
| 直接修改已有工具定义或描述 | 改变已有思考的前缀 | 使用会话中途工具变更；运行时发现工具按延迟加载规则处理 |
| 总结较早轮次，同时保留带思考块的最近轮次 | 最近思考原本依赖未压缩的完整历史 | 使用服务端压缩，或不再重放依赖旧前缀的思考块 |
| 从历史中间删除一个思考块 | 后续思考链失效 | 按允许的从旧到新清理方式处理 |
| 图片 URL 不变，但每轮返回不同图片 | 文档称检查的是获取内容的字节，不只是 URL 字符串 | 使用稳定文件引用或 Base64 |
| 从新模型回退到不兼容旧模型 | 本轮无法读取部分推理 | 记录模型不匹配事件，不要误判为前缀编辑错误 |
| 仅在尾部追加新消息 | 不修改原有思考之前的内容 | 正常追加；原样保留收到的 assistant 内容块 |

**核心迁移原则**：可以增加后续指令，也可以压缩上下文，但不能在改变历史的同时，假设依赖原历史的隐藏推理仍然有效。

### D. 三个具体边界例子

**例 1：改写系统提示后继续携带旧推理。**

第一轮在系统提示 S 下生成推理 T，第二轮把 S 改成 S'，但仍提交 T。按文档规则，T 的前缀不再匹配，应报错或被丢弃。即使 S' 只是增加当前日期，也属于历史变化。[2，“使用对话中途系统消息添加指令，而非编辑 `system`”]

**例 2：完整复制历史，然后分叉。**

如果分叉点之前的系统提示、工具和消息原样保留，在此基础上追加不同后续消息，文档允许已有思考继续使用。因此，不能把这项措施解释为“只要是一个新建会话对象，旧推理就绝对不可用”，也不能据此推导存在独立的会话 ID 绑定。[2，“常见问题：可以把一个对话的推理带到新对话中吗？”]

**例 3：回退旧模型，再切回原模型。**

文档称，模型不兼容造成的丢弃只针对该次请求，服务端不会改写客户端的 `messages`。如果客户端保留完整历史，之后切回兼容模型，且相关上下文仍有效，原先未向旧模型展示的思考可以再次被读取。若客户端自行删除这些块，则无法靠切回模型恢复。[2，“常见问题：当对话从 Claude Fable 5.1 切换到较早模型，然后再切换回来时，思考会发生什么？”]

这里的“丢弃”是**本轮不向模型提供**，不能一概理解为撤销签名、销毁密钥或永久删除客户端持有的推理。

### E. 部署范围与验证注意事项

本地文档记录：[2，“受影响的用户”]

- Fable 5.1 对 **2026 年 8 月 31 日 00:00 UTC 及之后创建的账号**默认强制检查。
- 旧账号可以通过设置 `prefix_mismatch_behavior` 主动启用检查。
- “后续模型将对所有用户强制执行”是该材料中的后续安排，不能据此认定所有线上模型现在已经执行。

以下是据此整理的**接入验证清单，尚未实测**：

1. 在测试环境记录连续请求的结构，检查 `system`、`tools` 和共有消息历史；日志需避免明文保存凭证和敏感内容。
2. 分开测试正常追加、前缀编辑、模型切换和客户端压缩，避免将不同失败原因归为同一类。
3. 前缀不匹配检查显式设置行为，不仅依赖测试账号的默认策略；批处理需要单独验证。
4. 监控 400 以及 `input_transformations`，确认“请求成功”是否伴随思考块丢弃。
5. 验证框架是否原样保存未知内容块、空 `thinking` 字段和签名，是否在模型回退时意外清空历史。
6. 客户端压缩避免拆开尚未完成的 `tool_use` / `tool_result` 往返；具体兼容处理应依照实际使用模型的官方文档验证。

### F. 这项机制仍不能证明什么

综合报告与本地补充材料，可以说它增加了上下文和模型兼容性约束；但不能进一步推导出以下结论：[1，pp.148–154；2，“工作原理”“常见问题”]

- **所有提取都已失效**：前缀绑定针对历史变更，不等于证明所有后续诱导、其他提取方式都无效。
- **账号身份已被绑定到每个推理块**：材料没有给出相应规则或密码学实现。
- **所有历史载荷已撤销**：材料没有披露旧签名统一失效或旧密钥销毁。
- **所有模型间迁移都被禁止**：兼容模型之间仍可保留思考。
- **最终答案无法用于训练**：保护隐藏推理不等于消除可见输出的训练价值。

因此，这项机制应被理解为报告分层防御中的一环，仍需要结合请求检测、访问风控和组织级处置，而不能替代这些措施。
