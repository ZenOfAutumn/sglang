# 《Stealing Reasoning Traces from Proprietary LLM APIs》中文说明

## 基本信息

- **中文译名**：从闭源大模型 API 中窃取推理轨迹
- **作者**：Alexander Panfilov、David Schmotz、Ilia Shumailov、Luca Beurer-Kellner、Joachim Schaeffer、Ameya Prabhu、Jonas Geiping、Maksym Andriushchenko
- **论文主页**：<https://stolen-thoughts.com/>
- **原始 PDF**：<https://stolen-thoughts.com/paper.pdf>
- **本地文件**：[`paper.pdf`](Stealing Reasoning Traces from Proprietary LLM APIs.pdf)
- **篇幅**：116 页（含附录）

## 一句话总结

论文发现，多家大模型服务商返回给客户端的“加密推理块”可以跨会话、跨用户，甚至跨同一服务商的不同模型重放；攻击者可把强模型生成的加密推理块交给防护较弱的小模型，将其当作“解密预言机”，诱导它输出隐藏推理，从而造成模型蒸馏、隐私泄露、绕过安全拒答和隐蔽提示注入等风险。

## 背景

推理模型通常先生成内部思维链（Chain of Thought，CoT），再输出用户可见答案。内部推理可能包含：

- 问题分解和中间推导；
- 工具调用结果；
- 用户隐私、凭据和上下文秘密；
- 模型的安全判断与拒答过程；
- 可用于蒸馏模型能力的高密度监督信号。

为了保护知识产权和敏感信息，一些 API 不再返回明文推理，而是返回摘要以及不可读的签名或加密载荷。客户端需要在后续请求中把该载荷原样传回，以便服务端恢复上下文。这样可以保持 API 无状态，减少服务端保存完整推理轨迹的成本。

论文将这类载荷概括为使用认证加密（AEAD）的“加密信封”。它通常包含密文、随机数、认证标签及模型或版本等元数据。现有设计能够保证载荷未被篡改，却没有充分约束载荷只能在原用户、原会话和原模型中使用。

## 核心漏洞

作者区分了三种兼容性：

1. **跨会话兼容**：同一用户可把旧会话中的推理块放入新会话，或改变推理块顺序。
2. **跨用户兼容**：一个用户获得的推理块可由另一个用户账号提交和处理。
3. **跨模型兼容**：同一服务商内，一个模型生成的推理块可被另一个模型接受。

其中跨模型兼容最关键。前沿模型通常有更强的防蒸馏和拒绝训练，而低成本模型的防护可能较弱。攻击流程可以概括为：

1. 获取强模型生成的加密推理块；
2. 将其注入同一服务商中兼容的弱模型请求；
3. 使用转录式越狱提示，要求弱模型复述它正在处理的先前推理；
4. 弱模型解密并读取该载荷，然后把内容输出为明文。

这并不是破解底层密码算法，而是利用“模型必须能够解密并处理载荷”这一事实，通过应用层行为让模型泄露解密后的内容。

## 论文展示的四类攻击

### 1. 推理蒸馏

攻击者能够获得强模型的中间问题分解、推导步骤和解题策略。与只收集最终答案相比，完整推理轨迹提供了更密集的训练信号，可能显著降低蒸馏闭源模型能力的成本。

论文还研究了将少量已提取的闭源模型推理作为前缀输入开放模型的现象。在作者的实验中，Kimi-K3 的后续推理和可见答案风格会向 Claude Opus 4.8 偏移。不过作者明确强调，这种行为相似性只能说明特定干预下存在异常兼容，**不能据此证明模型经过了蒸馏或记忆了专有数据**。

### 2. 绕过拒答并泄露危险信息

模型的最终回答可能经过安全过滤，但隐藏推理中仍可能讨论被拒绝输出的危险细节。攻击者可先让强模型围绕敏感问题进行内部推理，再借助弱模型提取该推理，绕过只检查最终输出的安全机制。

### 3. 隐私和凭据泄露

作者收集了 GitHub 和 Hugging Face 上公开的 **6,708 条智能体轨迹**，从中恢复出 **315,320 个推理块**。主要结果包括：

- 1,028 个推理块（约 **0.3%**）至少包含一项隐私泄露；
- 328 条会话（约 **4.9%**）至少泄露一项真实敏感信息；
- 汇总发现 **367 项个人身份信息（PII）**、**363 项技术标识符**和 **182 项凭据**；
- 在真实用户会话中，发现 62 个不同的 API Key、33 个密码、24 个访问令牌、7 个私钥、30 个个人邮箱和 6 个非本地 IP 地址；
- 真实会话中有 64 项泄露内容完全没有出现在可见聊天记录里。

最后一点尤其重要：用户即使清理了明文聊天记录，也无法检查或清理不可读的加密推理块，因此公开原始 API 日志仍可能泄密。

### 4. 隐蔽提示注入

攻击者可生成一个内部包含恶意指令的合法加密推理块，再把它植入公开或共享的智能体轨迹。受害者恢复该轨迹时，模型可能把载荷视为自己过去的可信推理并执行其中指令。

由于恶意载荷完全隐藏在加密块中，只检查可见文本的人工审查和外部安全监控很难发现它。论文通过概念验证展示了数据外传指令能够跨任务、跨模型规模影响后续行为。

## 实验与证据

作者在 Anthropic、OpenAI 和 Google 的模型生态中验证了推理块的兼容性及提取攻击，并使用 AIME 2025、Codeforces 和 Humanity's Last Exam 等任务收集受控推理轨迹。

由于研究者无法获得服务商内部的真实明文推理，论文不能逐字验证全部提取结果。其主要验证方法是比较：

- API 报告的原始思考 token 数；
- 提取出的文本重新编码后对应的 token 数。

二者在多数样本上高度接近，且提取内容通常明显比 API 提供的推理摘要更详细。作者据此认为提取具有较高保真度，但仍称弱模型为“模糊解码器”，并承认随机生成可能造成遗漏、改写或幻觉。

## 防御建议

### 服务端保存推理

最彻底的方案是不把推理密文交给客户端，而是在服务端保存推理状态，仅向客户端返回随机标识符。这样能消除可供窃取和重放的密文载荷，但会增加存储成本、状态管理难度和 API 复杂度。

### 将密文绑定到使用上下文

如果继续采用无状态 API，应把以下信息纳入 AEAD 的认证数据：

- 用户或租户标识；
- 会话标识；
- 当前模型或允许使用的模型范围；
- 推理块在对话中的位置；
- 前序消息或前序推理块的哈希。

论文给出一种简化的链式绑定形式：

\[
\tau_{n+1}=H\left(\text{user\_id}\parallel\text{session\_id}\parallel H(\tau_n\parallel\text{salt}_2)\parallel\text{salt}_1\right)
\]

其中，\(\tau_n\) 表示第 \(n\) 个推理块；得到的哈希被写入下一推理块的关联数据。服务端据此验证用户、会话和前后顺序，拒绝跨上下文重放。论文还建议结合 Merkle 树，以兼顾会话压缩、分叉和历史验证。

### 隔离模型与检测异常

API 网关应拒绝把一个模型生成的推理块交给不兼容或权限更低的模型，并监测以下异常：

- 同一签名被大量重复提交；
- 同一签名跨多个会话或账号出现；
- 短时间内大量触发解密错误；
- 大规模转录隐藏推理的请求模式。

### 密钥轮换和撤销

对于修复前已经发布的加密推理块，新增上下文绑定无法提供追溯保护。论文建议轮换旧密钥，并拒绝处理旧密钥签发的载荷；企业历史会话可在验证所有权后限期重新签发。

### 模型级防护

模型应专门训练为识别并拒绝“复述、转录或输出隐藏推理”的请求。但论文认为，仅依赖模型拒答不够稳健，必须与密码学绑定、网关隔离和异常检测共同使用。

## 对开发者和数据发布者的建议

1. 不要把签名、`encrypted_content`、`thinkingSignature` 或其他不透明推理字段提交到公开仓库。
2. 分享智能体轨迹前，直接删除所有推理块，而不是只清洗可见文本。
3. 将加密推理块视为潜在敏感数据，不要把“不可读”等同于“可安全公开”。
4. 对已经公开过原始轨迹的项目进行历史扫描，并轮换可能暴露的 API Key、密码、访问令牌和私钥。
5. 不要恢复或运行来源不可信的完整智能体会话，即使其中的可见文本看起来正常。
6. 企业应把这类字段纳入日志脱敏、数据保留、访问控制和合规审计范围。

## 局限性

- 实验针对作者在 2026 年 7 月测试到的特定 API 和模型版本，服务商可随时修改实现。
- 缺少真实明文推理作为逐字对照，token 数接近只能提供较强的间接证据。
- 对公开轨迹的扫描不是穷尽式审计，不能代表所有公开或私有数据集。
- 附录中关于开放模型与专有模型行为相似性的研究只显示相关性，不能建立蒸馏的因果结论。
- 论文称服务商在收到负责任披露后进行了缓解；截至 2026 年 8 月，文中主要攻击已无法按原方法复现。

## 评价与启示

这篇论文的关键贡献不是发现了传统意义上的加密算法漏洞，而是指出了**密码学保护范围与应用系统信任边界不一致**：载荷的完整性和机密性虽然受到保护，但合法解密者的范围过宽，且解密后的模型本身可以被提示操纵。

它带来三点重要启示：

1. **AEAD 只能保证“密文没有被篡改”，不能自动保证“密文只在正确上下文中使用”**。用户、会话、模型和顺序必须显式绑定。
2. **系统安全取决于模型家族中防护最弱的成员**。只加固旗舰模型，而允许低成本模型读取同一种推理载荷，会形成跨模型降级攻击面。
3. **对用户不可见的数据不应由用户承担清洗责任**。如果用户无法检查隐藏推理，服务商就需要提供更严格的隔离、生命周期管理和透明度保证。

总体而言，论文揭示了客户端保存加密推理这一架构在隐私、可移植性、成本和可审计性之间的深层冲突。对于生产级智能体系统，最实用的短期措施是删除共享日志中的所有不透明推理字段、轮换既往可能暴露的凭据，并在网关层禁止跨用户和跨模型重放。
